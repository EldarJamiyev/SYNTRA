# SYNTRA Architecture

SYNTRA uses a small local stack rather than a cloud AI service.

## Runtime components

1. **React/Vite frontend** — one active conversation view and one composer, with a compact history drawer for multiple named sessions. Session state is stored in bounded browser storage, the previous single-thread history is migrated on first load, and /clear erases only the active conversation. Search, rename, delete, resume, and storage-failure fallback are handled locally. Assistant Markdown is rendered without enabling raw HTML; links are protocol-checked before rendering.
2. **Node loopback service** — validates requests, owns chat jobs, keeps the active workspace, routes ordinary messages to chat, and coordinates repository edits.
3. **Local model backend** — if a suitable local Ollama model is installed, prompts are sent to that loopback Ollama service. Otherwise the router falls back to SYNTRA's local Python/PyTorch service. The native path is a from-scratch research model, not a pretrained frontier assistant.

The Node workspace server binds to 127.0.0.1. The frontend runs at 127.0.0.1:3000; the workspace API is proxied to 127.0.0.1:3001; the native AI service normally uses 127.0.0.1:3002; Ollama listens on 127.0.0.1:11434.

## Chat request lifecycle

1. The Node service checks whether the request is a clear software-change command. Broad verbs alone are insufficient: “write a poem” and “write an email” stay on the conversation path.
2. Before model loading, the service recognises a narrow set of network diagnostic requests (ICMP ping, local DNS lookup, one TCP port check) and runs them with bounded timeouts, validated hostnames/ports, and no shell command string.
3. For normal chat, it builds a bounded prompt from the latest message and recent conversation turns, counts tokens through the selected backend, trims excess history when required, and generates a local reply. Ollama NDJSON token chunks update the active chat job, and the UI polls those partial updates; the native research backend is currently non-streaming.
4. If the user explicitly asks to modify software, SYNTRA inspects the selected workspace, builds a local import graph (including recognised hidden project-config folders such as .github and .devcontainer), and ranks relevant source files.
5. The model is asked for a constrained JSON patch with exact search anchors and replacements.
6. The agent rejects malformed JSON, duplicate edits, ambiguous anchors, path traversal, sensitive file paths, and oversized changes.
7. Candidate edits are applied only to a temporary project copy. Available build, test, lint, and type-check scripts run with bounded timeouts. Inferred native test commands are selected from project manifests and matching test files; an empty test directory or a mismatched runner is not accepted as a passing test suite. Python checks prefer a workspace virtual environment when present, and timeouts terminate spawned process trees rather than only the top-level process. .NET project files and solutions are detected explicitly, but a .NET test command is selected only when a test project or test SDK is identified.
8. Failed checks are supplied as feedback for a bounded repair attempt. The original source is not modified during planning or verification.
9. If every discovered check passes and the patch does not modify tests or verification configuration, SYNTRA rechecks source hashes and applies the change with a backup and audit record. Dependency/build manifest or lockfile changes block automatic verification because sandbox dependencies are not reinstalled; changes to test or verification configuration require review even when checks pass. In those cases, proposals remain unapplied unless the user explicitly types /apply.

Before reporting a coding task, the agent also returns a bounded per-file diff preview generated from the exact original and candidate contents. Large changed sections are explicitly marked as truncated; the preview is for inspection, not a replacement for opening the full file. The chat response presents these diffs alongside the verification result and the explicit `/apply` instruction for proposals that were not automatically applied.

A passing check proves only that the project's discovered checks passed in the temporary copy; it does not prove the absence of defects.

## Workspace selection and proposal recovery

The active workspace is held by the local Node service. The frontend reads it from `GET /local-api/workspace/status`, restores the last selected folder from device-local browser storage, and switches the backend through the origin-checked `POST /local-api/workspace/switch` route. The selected path is validated by the same workspace resolver used by file operations. Workspace selection and conversation history are stored separately.

Unverified proposals are written under `.syntra/proposals` with the workspace root, original source hash, proposed content hash, and bounded change summary. The server reconstructs the pending queue from those files rather than relying on an in-memory list. It classifies a proposal as pending only when its current source hash still equals the recorded base hash; an already-applied proposal is omitted, and a changed source is marked stale. The `/proposals` command lists the restored queue, `/apply` rechecks hashes through the existing transactional apply path, and `/discard` removes selected queue records after explicit user intent without touching project files. A new coding task is blocked while pending or stale proposals remain, preventing a later request from silently replacing an earlier review queue.

The browser remembers the selected workspace path locally. That value is untrusted input and must pass workspace resolution before it can become active. The server remains loopback-only; switching projects does not expand its network exposure.

## Durable agent runs and recovery

Coding tasks are recorded in the active workspace under `.syntra/runs`. Each bounded JSON record stores the task goal, lifecycle state, plan steps, selected source files and hashes, local model/context metadata, attempts, tool-call summaries, verification results, changed-file hashes, proposal IDs, event history, and—only after validation—a bounded patch checkpoint. The run store retains at most 40 recent records per workspace; individual records are limited to 160 KB. The run directory is validated against symlink redirection.

`GET /local-api/agent/runs` is read-only: refreshing the browser does not change the status of a live task. The local service marks unfinished runs as interrupted once during startup recovery, and also recovers runs when a different workspace is selected. Reopening the workspace panel refreshes the current run list, so a service restart can be reflected without a browser reload.

The Stop action aborts the active model request and supported project-check process tree. Cancellation is rejected once a transactional proposal apply has begun; a cancellation arriving immediately before apply is checked before the transaction starts. Any proposals already staged remain in the workspace review queue and are not silently discarded.

Resume is deliberately conservative. A single-slice run with a saved validated patch re-runs workspace inspection and validates the patch against exact original file hashes and anchors before continuing through candidate checks and proposal staging. If the original source has changed, SYNTRA refuses to reuse that patch. Existing pending or stale proposals must be resolved before resuming.

Multi-slice runs persist a separate candidate checkpoint after each independently verified non-final slice at `.syntra/runs/<run-id>.candidate.json`. The checkpoint stores only the cumulative changed-file contents and their original workspace baselines, the validated slice plan and next-slice index, plus a bounded verification summary. Storage is limited to 24 changed files, 128 KB per file, and 512 KB per checkpoint. It is associated with the run ID and canonical workspace root, uses the regular-file/symlink protections used by other local state, and is written atomically. On resume, SYNTRA validates the checkpoint schema, every candidate content hash, every original-file hash, and whether paths that were previously new remain absent. A stale, malformed, or mismatched checkpoint is rejected; it is never blindly copied into the real project. A valid checkpoint is reconstructed in a fresh temporary candidate directory, then re-inspected and re-ranked before the next slice is generated. If interruption occurs while a slice is in progress—or after the final slice passes but before proposal staging—the next resume regenerates that in-flight/final slice from the last verified candidate boundary. A checkpoint is accepted only when at least one slice remains pending; SYNTRA never persists an all-slices-complete checkpoint that could skip final candidate verification. If there is no completed verified slice, SYNTRA starts from the overall task goal. Candidate state is removed after final proposal staging; failure to persist a checkpoint is explicitly recorded and does not pretend that restart continuation is available.

This is bounded multi-step orchestration, not arbitrary workflow execution. Before editing, the local model may propose up to three ordered implementation slices with explicit acceptance criteria; SYNTRA validates the plan and can fall back to one slice. Each slice is patched against the current candidate workspace, verified in that same workspace, and followed by a fresh inventory/import-graph inspection before the next slice begins. A failed check triggers a bounded repair attempt after re-inspection. Final proposals are aggregated against the original project-file contents and base hashes, not against intermediate candidate versions. Single-slice recovery retains the existing exact-hash patch validation behavior.

## Permissioned tool runtime

`local/tool-runtime.mjs` is the shared registry for local workspace operations. `GET /local-api/tools` returns the 21 tool definitions and their input schemas, permission classes, and approval requirements. `POST /local-api/tools/execute` validates calls against those definitions; unknown tools, undeclared fields, malformed IDs, out-of-range line windows, and invalid types are rejected.

The current registry contains:

- Read-only tools: `workspace.inspect`, `workspace.index.status`, `workspace.checks.discover`, `workspace.search`, `workspace.symbols.search`, `workspace.read`, `workspace.proposals.list`, `git.status`, and `git.diff-summary`.
- Local SYNTRA-state writes: `workspace.index.refresh`, `workspace.plan`, and `workspace.proposals.stage`. Index refresh writes only bounded index metadata under `.syntra`; proposal staging writes hash-bound proposals and does not alter project source.
- Approval-gated operations: `workspace.check` (executes project-defined checks), `workspace.proposals.apply`, `workspace.proposals.apply-many` (transactional source changes), and `workspace.proposals.discard` (irreversible deletion of proposal records).

Every accepted tool invocation receives a UUID run ID and emits started/completed/failed or approval-required records to `.syntra/actions.jsonl`. Events contain bounded input/output summaries, permission and approval decisions, duration, and errors; source contents and full file excerpts are deliberately excluded. An initial audit-write failure prevents the operation from running. A final audit-write failure is returned as an explicit warning because an already-completed operation cannot safely be represented as not having happened. Calls for one workspace are serialized to prevent overlapping proposal, check, and audit operations.

The incremental workspace context index is stored per workspace at `.syntra/workspace-index-v2.json` (schema version 2). It extracts lightweight declaration metadata for JavaScript/TypeScript, Python, Go, and Rust; resolves local JS/TS and Python imports, module-local Go imports declared by `go.mod`, and common Rust `mod`/`use crate` relationships; records relative Markdown/MDX/reStructuredText links; and heuristically associates test files with likely source owners by basename, falling back to resolved source imports. Refresh hashes every indexed file, reuses parsed declarations and unresolved references when hashes are unchanged, recomputes graph edges from the current file set, reparses modified files, and drops deleted or unreadable entries. The index stores relative paths, sizes, content hashes, declaration names/kinds/line numbers, bounded import specifiers, and resolved path relationships—not source-file bodies or documentation text. Symbol-search results and returned relationship paths are checked against current file hashes. Parsing and ownership are bounded heuristics, not a compiler, full language-server index, or authoritative test-coverage map.

Project memory is separate from the symbol/context index and is stored per workspace at `.syntra/project-memory-v1.json`. It contains only notes explicitly entered by the user through the workspace panel or an approved tool call; SYNTRA does not automatically ingest chat history, source files, or documentation into memory. Notes are limited to 200 per workspace, 1 MB total, 120-character titles, 2,400-character bodies, and eight short tags. Supported categories are architecture, convention, decision, workflow, testing, and other. The store is bound to the resolved workspace root, validated before updates, written atomically, and rejects symbolic links. Updates and deletions use an expected-update timestamp to avoid overwriting concurrent edits. A best-effort detector rejects common credential formats, but it is not a guarantee that every secret can be identified—never use project memory as a credential store.

The tool registry exposes `workspace.memory.list` and `workspace.memory.search` as read-only operations. `workspace.memory.add`, `workspace.memory.update`, and `workspace.memory.delete` require explicit approval and are not permitted in model-selected retrieval plans. Approved memory operations write only bounded metadata to `.syntra/actions.jsonl`; note titles and bodies are intentionally omitted from audit summaries. The agent may select only bounded memory search, and treats retrieved note contents as untrusted project context rather than instructions.

For multi-slice tasks, SYNTRA keeps a single temporary candidate workspace for the entire bounded run. After a slice passes all discovered checks and cumulative candidate-integrity checks, it re-inspects the candidate with `workspace.inspect`, rebuilds the import graph, refreshes ranked file context, and may run another bounded read-only model retrieval plan for the next slice. On failed verification, it performs the same re-inspection before a repair request. The final change set is reconstructed from the original workspace baseline and the intended cumulative candidate contents, so a file edited in several slices produces one proposal with the original base hash. The final proposal is not applied when any slice is incomplete, any check fails, or any candidate integrity check fails.

The agent records read-only Git status and diff-summary observations before patch generation; command output is bounded and treated as untrusted context rather than instructions. After applying a candidate patch to its temporary copy, it invokes `workspace.checks.discover`. That tool uses the same runner-selection logic as project-check execution and reports only build/test/lint/type-check tasks with a supported runner; discovery itself never executes project code. The agent then runs those checks through the approval-gated `workspace.check` tool. After checks finish, it re-reads every changed candidate file through `workspace.read` and compares its SHA-256 hash with the validated patch. If a check script modifies or removes a changed file, candidate-integrity verification fails and the result cannot be treated as passed. The temporary copy is discarded after the run. Bounded observation records are stored with the agent run under `.syntra/runs`, and the workspace panel shows their count.

Before patch generation, the local model may select up to four bounded context-retrieval calls from the read-only `workspace.search`, `workspace.read`, and `workspace.symbols.search` tools. The symbol index is refreshed against the active candidate before retrieval; symbol results are limited and revalidated against current file hashes. The plan is parsed and validated against a strict allowlist: search queries are bounded, reads may reference only paths in the already-discovered safe source graph, and each read is limited to 200 lines. Calls execute through the same audited tool registry as all other operations. The agent validates the result against those three tool names before execution. An invalid or over-budget plan is rejected and the deterministic relevance-ranked context remains the fallback. The selected snippets are passed to patch generation as untrusted repository data. This is limited model-selected retrieval, not arbitrary tool selection: no model-selected check, source write, proposal apply/discard, terminal command, or network action is possible in this step.

The coding agent routes project inspection, candidate checks, proposal staging, and transactional apply through this registry. It now uses a bounded model-generated slice plan to divide larger tasks into up to three independently checked increments. Candidate files are accumulated in one temporary workspace, and the source changes are staged only once the slice loop ends. If any planned slice remains incomplete, the combined result is explicitly unverified and cannot enter the automatic apply path. The rest of the control flow remains deterministic: the local model cannot select check, write, apply, terminal, or network tools. A candidate copy is not an OS-level security sandbox: approved project scripts run with the current user's normal filesystem and network privileges. Users should run these checks only for repositories whose scripts they trust. Git inspection uses fixed `execFile` arguments, disables optional index writes and external diff, and does not contact remotes. There is no general-purpose terminal tool in this phase.

## Model and context handling

Ollama discovery excludes cloud-tagged models and rejects weights files larger than 70% of physical RAM to preserve working memory for the OS and inference context/cache. Stored weight size is a heuristic, not a guarantee of runtime fit. Model detection is briefly cached between adjacent chat stages; injected/test fetch implementations bypass the cache for deterministic testing. The Ollama router uses an 8,192-token default context, configurable with SYNTRA_LOCAL_CONTEXT within the supported limits.

The native Transformer has its own tokenizer, context configuration, training loop, checkpointing, and inference implementation. Its weights start randomly initialized. Training it from scratch on a small project is useful for runtime research, but does not confer reliable general knowledge or frontier-model coding ability.

## Reliability and security boundaries

- File access is rooted in a selected absolute workspace, with path traversal and symlink path components blocked. The reserved .syntra state directory and its proposals/backups/plans subdirectories must be real directories inside that workspace, and the audit log must be a regular file; none may be symlinks to external paths.
- Likely credential files and secret paths are excluded from workspace read/edit operations.
- Agent patches are restricted to recognized text/source/configuration files and validated against exact file hashes. Multi-file apply preflights every proposal, saves backups together, rechecks each source immediately before writing, and attempts a guarded rollback if a later write fails.
- Candidate checks execute in a temporary project copy. Build/test scripts are project code and should still be reviewed when working in an untrusted repository.
- The services are intended for local use, not direct internet exposure. Run checkpoints, proposal state, and tool audit data remain inside the selected workspace's .syntra directory; deleting that directory removes the local recovery history. Automated Node tests launch an isolated loopback server on a temporary port to check request validation and origin rejection. A static hosted copy cannot access the user's local model or workspace agent by itself.
