# Grill with docs

Use only when the user explicitly requests a design interview or a decision workshop.

1. Read the existing glossary, ADRs and implementation before asking questions.
2. Resolve factual uncertainties from source code and documentation yourself.
3. Ask focused questions about unresolved product or architecture decisions; do not ask about implementation details the engineering team can determine.
4. Create or update an ADR only after the decision is confirmed. Capture context, considered options, decision, consequences and date.
5. Update the glossary only for stable, agreed domain language. Avoid speculative terms and duplicate context.
6. Link decisions to affected modules and tests. When implementation is requested, continue beyond documentation and implement the agreed work.

Do not write an ADR merely to make a routine change look formal.
